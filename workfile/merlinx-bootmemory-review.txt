按 Claude 的 8 条逐条核对
-------------------------

1) initrd/FDT 是否会被分配器当成空闲内存
   现状：MapReserved() 只有在 GCD 类型是 NonExistent 时才 AddMemorySpace(Reserved)。
   如果类型已经是 SystemMemory，它只 SetMemorySpaceAttributes(WB)，没有把范围占住。
   当前地址布局下，initrd 0x47c80000、DTB 0x4bc80000 位于 MemoryMapLib 的
   DXE Heap 末尾 0x43f80000 和 ATF 0x4ce00000 之间，预计是 NonExistent，
   所以当前路径会 AddMemorySpace(Reserved)，大概率能工作。
   但这是地址布局的巧合，不是驱动的保证。需要处理 SystemMemory：
   用 gBS->AllocatePages(AllocateAddress, EfiReservedMemoryType, pages, &base)
   占住，或使用能够把 SystemMemory 转成 Reserved 的路径。
   另外 MapReserved() 只检查 Base 一个 descriptor；如果范围跨 descriptor，
   AddMemorySpace 可能失败。
   结论：需要修，至少加 SystemMemory 分支。

2) Depex = TRUE
   现状：INF 最后是 [Depex] TRUE。
   已核对 Mu_Basecore 的 Gcd.c：SetMemorySpaceAttributes() 在
   CpuArchAttributes != 0 且 gCpu == NULL 时返回 EFI_NOT_AVAILABLE_YET
   （MdeModulePkg/Core/Dxe/Gcd/Gcd.c 约 936 行）。
   当前 MapReserved() 不检查 SetMemorySpaceAttributes 的返回值，失败后仍然读 FDT，
   这会在未映射的地址上直接取指/取数，可能 HardFault。
   结论：必须改成 gEfiCpuArchProtocolGuid，并把映射失败向上返回。

3) initrd 属性长度和 FDT 窗口
   现状：ReadCells() 支持 4/8 字节，PublishInitrd() 也接受 length 4 或 8。
   实测 workfile/merlin.fdt 的 /chosen 属性：
     linux,initrd-start = <0x47c80000>   (4 字节)
     linux,initrd-end   = <0x47dcb76e>   (4 字节)
   所以当前设备走 4 字节分支，代码可读。
   FDT 实际 totalsize = 252320 (0x3d9a0) 字节。
   但驱动固定 MapReserved(Dtb & ~2MB, +4MB, ...)，没有用 FdtTotalSize 缩小窗口。
   当前 DTB 约 0x4bc80000，4MB 窗口是 0x4bc00000-0x4c000000，
   还没碰到 ATF 0x4ce00000；但这是靠地址巧合。
   建议：先映射 8KB 头窗口读 header，校验 magic/totalsize 和溢出，
   再按 align(Dtb) 到 align(Dtb + totalsize) 映射实际范围；
   不要再固定 4MB。这样也不会把相邻 LK/ATF 区域拉进 GCD。
   结论：属性长度没问题；FDT 窗口需要修。

4) 空 ramdisk
   现状：属性缺失、长度不对、End <= Start 都会 DEBUG 后 return；
   没有 ASSERT，没有死循环。空 ramdisk 是容忍的。
   如果 LK 对空 ramdisk 不写属性，就不会有 BlockIo，这是预期行为。
   结论：当前代码安全；Stage 2 需要占位 ramdisk 时再另做。

5) 固件卷容量和三个大小
   现状：本次构建成功，FD 正好 0x300000；FVMAIN 只剩 0xe78 (3704) 字节。
   Resources/Configs/merlinx.toml [uefi_fd] size=0x300000；
   BootShim 编译时使用同一个 size；merlinx.fdf 使用 $(FD_SIZE)。
   三个数字当前一致。
   注意：FVMAIN 只剩 3704 字节，再加入驱动/字符串很容易溢出；
   不要在这个基础上继续加功能而不清理。
   结论：容量当前够，但余量很小。

6) 屏幕日志
   现状：所有成功日志都用 DEBUG_ERROR；没有 gBS->Stall，也没有 ReadyToBoot 二次打印。
   如果 DebugLib 走串口而设备没有 UART，屏幕上看不到；
   即使能看到，后面的 GOP/控制台初始化也可能把它清掉。
   建议：测试镜像里在关键日志后 gBS->Stall(3-5 秒)，或注册 ReadyToBoot
   事件再用 gST->ConOut 打一次摘要。
   结论：验证手段缺失，不是驱动正确性问题。

7) BlockIo 细节
   现状：
   - Write 返回 EFI_WRITE_PROTECTED：有
   - Media->ReadOnly = TRUE：有
   - LogicalPartition = FALSE：有
   - LastBlock = size/512 - 1：有，且 Size < 512 会提前 return，不会下溢
   - 设备路径含 End 节点：有
   - Vendor GUID 唯一：有
   - BufferSize 非 512 倍数返回 EFI_BAD_BUFFER_SIZE：有
   - Lba 越界检查在减法之前：有
   结论：BlockIo 本身基本符合要求。
   真正的风险是 MapReserved 失败后仍然设置 mRamBase 并安装 BlockIo，
   之后一读就访问未映射内存。这个要和第 1/2 条一起修。

8) 不要把 DTB 的 /memory 当成可用内存
   现状：这个驱动没有使用 /memory，也没有把 /memory 加进 GCD；
   所以当前没有这个错误。后续 Stage 7 加可用内存时，
   必须从 /memory 和 atag,mem 中扣掉 framebuffer、TEE、SSPM、SCP、MD、ATF、
   pstore、videolfb 等区域。MemoryMapLib.c 已经把 framebuffer head/display/tail
   等区域列为 Reserved，但后续加 SystemMemory 时仍需逐段排除。
   结论：本驱动不需要改；后续阶段注意。

其他需要一起看的点
------------------
A. MapReserved() 是 VOID，失败只打日志，调用方继续执行。
   这是当前最危险的结构性问题。建议改成返回 EFI_STATUS：
   - GetMemorySpaceDescriptor 失败 -> 返回
   - NonExistent: AddMemorySpace(Reserved)，失败返回
   - SystemMemory: AllocatePages(AllocateAddress, EfiReservedMemoryType)，失败返回
   - SetMemorySpaceAttributes 失败 -> 返回（如果刚分配，FreePages）
   - 调用方：FDT 映射失败就不 FdtCheckHeader；initrd 映射失败就不安装 BlockIo。

B. FDT 头窗口建议：
   HeaderBase = Dtb & ~0xFFF
   HeaderSize = 0x2000（8KB，覆盖跨页的 40 字节头）
   先映射 HeaderBase..HeaderBase+0x2000
   再 FdtCheckHeader，读 FdtTotalSize
   校验 Total >= sizeof(FDT_HEADER)、Dtb + Total 不溢出
   ActualEnd = ALIGN(Dtb + Total, 4KB)
   如果 ActualEnd > HeaderBase+0x2000，再映射尾部
   注意：8KB 头窗口会有最多 8KB 的过度保留，但比 4MB 小得多。

C. 当前构建的 FD 已经包含新驱动，但 Depex 仍是 TRUE，且 MapReserved 失败会继续；
   不建议直接把这个 FD 上机做 Stage 2 验证，先修 1/2/3。
